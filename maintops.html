01 / MaintOpsMaintenance operations platform

Who owns this fault, and is it late?

MaintOps handles maintenance work for a single organization: a requester reports a fault, a supervisor triages and assigns it, a technician does the work, and SLA cycles record whether the targets were met. The source is public; there is no hosted instance.

01 / Product

Three operational roles, and one privilege that is not a role.

Maintenance work fails in the gaps between people: a fault gets reported to nobody in particular, or two technicians assume the other took it. MaintOps gives every fault an explicit owner and an explicit clock.

who does what

  • RequesterReports faults, follows public updates, confirms or reopens resolved work
  • TechnicianStarts assigned work, places it on hold, resumes, documents and resolves
  • SupervisorTriages the queue, assigns and reprioritizes, monitors SLA performance, sees internal notes
  • Account administratorA separate privilege, not a fourth role — held alongside an operational role

That last distinction matters in the data model as much as the interface. is_account_admin is a flag beside the operational role, so a supervisor who also administers accounts keeps one identity and one queue rather than needing a second login. Public registration can only ever create a requester; every privileged role is assigned administratively and audited.

02 / Architecture

Three runtime layers, one authorization point.

03MySQLRecords · SLA state · audit history

Backend capabilities are sliced by business area, and each one separates the same way: routes and schemas hold the HTTP contract, controllers adapt request and response, services own authorization and business transactions, repositories own parameterized SQL and row locking, and presentation helpers shape safe responses. The frontend is organised by the same operational domains, so a feature is one folder on each side rather than a trail through shared layers.

Ticket lifecycle changes run inside database transactions and write immutable events. Assignments, comments, internal notes, SLA cycles, notifications and AI suggestions all reference the ticket instead of overwriting it, so history is append-only by construction rather than by convention. All database sessions are normalized to UTC and the client does the formatting.

background workers

  • Durable stateWorker state lives in database rows, not in memory
  • RecoveryWorkers resume on restart rather than losing queued work
  • ScopePending-registration cleanup, SLA checks, queued email delivery
  • MailConsole transport is a local simulation; SMTP is configured explicitly

03 / Lifecycle & SLA

Every ticket carries a cycle, and every cycle carries its targets.

A ticket moves through a fixed set of transitions, each one authorized and each one recorded. Running alongside it is an SLA cycle with two independent targets: how long until someone starts work, and how long until it is resolved.

technical artefact · lifecycle against the SLA cycle

  1. 01RequestCycle opens · both targets set from the matched policy
  2. 02TriageCategory and priority set · priority selects the targets
  3. 03AssignmentAn owner exists · work-start target still open
  4. 04Start workWork-start time recorded · resolution target still running
  5. 05Hold / resumeRecorded on the ticket — the resolution clock keeps running
  6. 06ResolveResolution time recorded · cycle closes
  7. 07Confirm or reopenReopening starts a new numbered cycle rather than reviving the old one
  8. 08CloseTicket settles · every cycle stays on the record

Two decisions in there are worth naming. A hold does not stop the clock. Placing work on hold is a real state on the ticket, but the SLA monitor still counts on_hold among the statuses it watches, so an aging held ticket stays visible instead of disappearing behind a paused timer. And a reopen does not resume the old cycle — it opens a new one with the next cycle number, so a ticket resolved once and reopened twice reads as three measured attempts rather than one long ambiguous span.

how a policy is chosen

  • Match scopeCategory and priority, priority alone, or the organization default
  • TargetsSeparate work-start and resolution minutes per cycle
  • SnapshotThe policy name is copied onto the cycle when it opens
  • MonitoringA background worker evaluates open cycles and raises notifications

04 / Access & security

The frontend improves navigation. It does not decide access.

Role guards and hidden buttons in the SPA exist so people are not offered actions they cannot take. They are a convenience layer over a decision the server has already made, and the project documentation says so directly: frontend guards improve navigation and feedback, but they are not a security boundary.

decision 01

Put authorization in the service layer, beside the transaction

Constraint
Four privilege combinations act on the same ticket from different screens.
Decision
Services own authorization and run it inside the same transaction as the state change.
Result
An unauthorized write cannot half-apply, and the interface can only ever reflect what the server already enforces.
Trade-off
Every new transition needs its own authorization rule and its own test; none of it can be inferred from the route.
Sessions
JWT carried in a secure cookie. Deactivation, role change, and administrator grants invalidate live sessions through token versioning.
Registration
Email-verified, with attempt limits, a resend cooldown and an hourly cap. Unverified accounts wait in a separate table and are cleaned up by a worker.
Sign-in abuse
A dedicated rate-limiter plugin sits in front of login.
SLA policies
Versioned. Editing a policy already in use creates a new version instead of rewriting how past tickets were measured.
Attachments
Bytes live outside the web root; metadata and authorization context live in MySQL and downloads pass through an authorization-checked route.
Audit
Account, administration and SLA-policy changes each write to their own audit tables.

The demo seed refuses to run when NODE_ENV is production or when the target database name does not contain demo, test or release_check, and it takes its password from the environment rather than printing one.

05 / Bounded AI

Four narrow features, and none of them can change a ticket.

MaintOps can draft a request, summarize a ticket for the person reading it, suggest triage values, and rank possible duplicates. It has no chatbot, no tool calling, no web access, no code execution, no attachment interpretation, and no ability to mutate workflow state. With AI disabled or the provider unreachable, the maintenance workflow is unchanged.

technical artefact · where an AI request can fail closed

  1. 01Untrusted inputTitles, descriptions, comments — still untrusted after authorization
  2. 02Input screeningBounded chunks scanned by Prompt Guard; suspicious or unavailable fails the request closed
  3. 03Bounded contextOne of five named profiles, each with an explicit exclusion list and a character ceiling
  4. 04ProviderFixed versioned instructions, no tools configured, strict JSON Schema requested
  5. 05Local revalidationAjv re-checks lengths, enums, evidence allowlists, markup, URLs and control characters
  6. 06Discard or holdInvalid output is discarded whole — never partially repaired into something valid
  7. 07Human approvalA triage suggestion stays pending until a supervisor accepts it
  8. 08Workflow stateApplied through the same authorized transition as a manual edit

The screening step is the one I would defend hardest. Prompt Guard is used through its own binary-classifier contract — the returned probability is validated as a number between 0 and 1 and compared against a configured threshold — rather than being asked to emit JSON like the main model. Treating a classifier as a classifier removes an entire category of parsing failure, and if it is unavailable the AI request fails rather than proceeding unscreened.

limits, from configuration

  • Per userRequests per minute and per day are both capped
  • GloballyBounded concurrency, a request timeout, and a failure circuit breaker
  • ContextOlder public events are dropped first; the request fails safely if essential context still will not fit
  • LoggingInteraction records store metadata only — never prompt, context or output — and are purged on a schedule

06 / Boundaries

What this project does not claim.

Deployment
There is no hosted instance and no public demo. The README documents how to run it; nothing is running.
Usage
No user counts, uptime figures or availability numbers exist, because the system has not been operated in production.
Interface evidence
No screenshots are committed. The project's own demo notes warn that interface images leak names, addresses and machine details, so captures have to come from the synthetic demo database.
Licence
Proprietary. The source is published for academic evaluation and portfolio review, not for reuse.

what it demonstrates

A layered API with authorization in the service boundary, a versioned SLA model that survives its own policy edits, append-only operational history, background workers with durable state, and an AI integration designed around its failure modes.

what it is tested with

Backend cases run on the native Node test runner against the real service and repository boundaries; the frontend is covered with Vitest and Testing Library. Both suites are in the public repository.
