ProcBeacon is a Windows desktop tool I built for my own development work. It reads the system's port and process tables, links what it finds to the project folders I register, and checks a process's identity again before it ends it. It is packaged as a local, unsigned preview and is not distributed.

01 / Why it exists

Port 5173 is taken. By what, and from which project?

A day of web development leaves Node servers, watchers and test runners behind. Windows can tell you that a PID owns a port. It cannot tell you which of your projects started it, whether it is the same process you saw a minute ago, or whether ending it is safe. ProcBeacon answers those questions in one window.

four areas, one search

  • WorkspacesRegistered project folders and services, the processes attributed to them, configured tasks and managed sessions
  • PortsTCP and UDP endpoints over IPv4 and IPv6, an exact local-port lookup, a sampled timeline and explicit loopback checks
  • ProcessesCPU, working set, runtime, endpoints and workspace attribution, with guarded actions
  • SystemCPU, memory, disk and network, with the processes using the most. Ctrl+K searches services, names, PIDs and ports

02 / Architecture

One monitor, and the native code kept in one place.

{{> case-cut procbeacon}}

The solution is split by what each part is allowed to know. The core holds the rules and targets plain .NET, with no Windows dependency. The Windows layer owns every native call and turns raw system tables into typed snapshots. The WPF application binds view models to those snapshots, and a small command-line tool exercises the collectors on their own.

One monitor coordinates refreshes for all four areas. Scans are serialized, cancellation is honoured, and a late callback from a cancelled scan is discarded rather than painted over newer data, so switching areas never shows two different moments at once.

native sources, from the code

  • EndpointsGetExtendedTcpTable and GetExtendedUdpTable from IP Helper, with the owning PID
  • IdentityOpenProcess, GetProcessTimes and QueryFullProcessImageNameW
  • MetricsPDH counters for CPU, disk and network; GlobalMemoryStatusEx for memory
  • UnknownsA value it cannot read or map is shown as unknown, never filled in

03 / Ports & attribution

Every link between a process and a project says how it was made.

A process is attributed to a workspace only on evidence, and the label says which kind. It is inferred when a Node process's entry point resolves under exactly one registered folder and its native identity matches; explicit when I associate that exact process myself, after a fresh native check; and unknown when evidence is missing, relative, expired, conflicting or ambiguous. In the validation runs, five controlled Node processes produced three correct inferences, two unknowns and no false automatic attribution.

Reading a Node process's command line is opt-in. Only after consent, and only for my own account's Node processes, does ProcBeacon read it, keep the entry point and discard the rest. No command line reaches the interface, the logs or an export, and the environment, .env files and scripts are never read. Revoking consent clears what is held in memory.

Port lookups are exact and say what they cannot know: the inspector lists every endpoint on the port with the time of its snapshot, and states that the absence of a row does not prove the port is free.

04 / Process safety

Windows reuses process IDs, so identity is checked on the handle that acts.

Windows reuses process IDs: between looking at a row and clicking, the PID can belong to a different program. ProcBeacon therefore identifies a process by its PID and its creation time, and acts only through a handle whose identity it has just verified.

technical artefact · where a terminate request can stop

  1. 01PreflightRefused at once if the snapshot lacks a creation time or path, or points at ProcBeacon itself
  2. 02OpenA handle is opened for the PID; the process object cannot be recycled while it is held
  3. 03Re-verifyOn that handle, PID, creation time and full path must match the confirmed snapshot
  4. 04CriticalityIsProcessCritical, PIDs 0 to 4 and protected processes are blocked
  5. 05ConfirmThe dialog states the risk; the action stays disabled until it is acknowledged
  6. 06One shotA prepared session works once; another click needs a new confirmation
  7. 07ActIdentity is checked again on the same handle immediately before TerminateProcess
  8. 08ReportExited, already exited, denied, blocked or identity changed: reported as it happened

decision 01

Identify a process by PID and creation time, on one handle

Constraint
Windows reuses process IDs, so the PID on screen can name a different program by the time you act.
Decision
Open a handle first, then compare PID, creation time and executable path with the confirmed snapshot on that same handle, and check again just before acting.
Result
A changed identity, a critical or protected process, or ProcBeacon itself is refused before any request reaches Windows.
Trade-off
A process that cannot be opened or read is never offered an action, even when ending it would be harmless.

Managed sessions follow the same rule from the other side. ProcBeacon starts only explicit executables, keeps their output in bounded buffers, and can force-end only the root process it created. It says plainly that an orderly stop is not supported and that child processes may survive.

05 / Reliability & tests

438 tests, and native checks only against processes the tests own.

The solution builds with warnings treated as errors and nullable reference types enabled. In a Release build on 21 November 2026, 438 automated tests pass: 69 for the core rules, 108 for the Windows layer and 261 for the application.

Native checks
Windows-layer tests start their own fixture processes and endpoints, then inspect and end only those.
Persistence
Workspace and task registries are written to a temporary file and swapped in with File.Replace and a backup; failures in the middle of the replace are injected and tested.
Monitor
Repeated refreshes, pause and resume, collectors that ignore cancellation and late callbacks are all exercised.
Rendering
The application's own WPF views are rendered offscreen with fixture data. Those renders are the screenshots on this page.
Packaging
A self-contained .NET 10 build for Windows 11 x64 is packaged as a per-user Setup and a ZIP, version 0.1.0-preview.1 (22 November 2026). All 416 files match by path, size and SHA-256 across the publish folder, the Setup payload and the ZIP, and 92 fixture scenes load from the packaged files with no binding errors.

06 / Boundaries

Packaged locally, not distributed: the preview is unsigned, and there is no public release. Installing, reinstalling and uninstalling on a clean test machine, a licence and approval to publish are still pending.
