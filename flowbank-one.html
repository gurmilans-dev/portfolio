01 / Product

A retail bank’s everyday screens, on fictitious accounts.

I wanted a project where being wrong has a precise meaning: money appears, disappears or moves twice. FlowBank One simulates a retail bank end to end, and its demo users have months of history generated through the same posting path as every transfer, so the screens show what the ledger actually holds.

what it does

  • AccountsChecking and savings accounts, amounts in minor units, account numbers with a mod-97 check
  • StatementThe ledger itself, newest first, filtered by direction and by Italian calendar days
  • TransfersFour steps: details, payee check by masked name, confirmation, receipt
  • AnalysisSpending by category and six months of money in and out, from an event-fed projection

The interface and the design documents are Italian; the code and its comments are English. The sidebar says what the product is on every screen: a simulated bank for demonstration, with no real money.

02 / Architecture

One process, eight modules, and walls between them.

{{> case-cut flowbank}}

It is a modular monolith on purpose: one deployable, but eight modules (ledger, identity, audit, analytics, notifications, simulation, platform and shared) whose allowed dependencies are declared in each package and enforced by a test that fails the build when one module reaches into another. Each module owns its own PostgreSQL schema, with no foreign keys across schemas.

When the ledger needs something only identity knows, such as the masked name of an account holder or a user's current security version, the platform module declares a small interface and identity implements it. The dependency points the right way, and the ledger never imports identity.

14 architecture decision records, among them

  • RuntimeSpring MVC on Java 21 virtual threads, rather than a reactive stack
  • PersistenceJPA for the domain, native SQL for analysis, hand-written Flyway migrations; Hibernate only validates the schema
  • One data storePostgreSQL for ledger, sessions, audit, outbox and analytics alike
  • Real database in testsIntegration tests run against PostgreSQL in a container, never a substitute

The spending analysis is a projection, not a query over the ledger. A transfer writes its event in its own transaction (a transactional outbox); a worker delivers each event with FOR UPDATE SKIP LOCKED, at least once, and the projection is keyed by ledger entry, so applying an event twice changes nothing.

03 / Ledger & concurrency

Double-entry, enforced by the database as well as the code.

Every transfer writes two ledger entries, a debit and a credit, in one transaction. Amounts are integers in minor units with overflow-checked arithmetic, so nothing is ever rounded. The database is the last line of defence rather than an afterthought:

Balanced
A deferred constraint trigger, checked at commit, rejects any transfer whose debits and credits differ.
Append-only
The application's database role can insert ledger rows but never update or delete them; on accounts it may update only the balance, sequence and status columns.
Sequenced
Each entry carries its account's next sequence number, unique per account, and the balance after it. The statement reads both directly.
Shaped
Check constraints cover amounts, currencies, account-number format, minimum balances and closed accounts; composite keys tie each entry to its account's currency.

technical artefact · one transfer, from click to commit

  1. 01DetailsThe amount is parsed without floating point; the account number is checked before sending
  2. 02KeyThe browser creates an idempotency key and keeps it until it knows the outcome
  3. 03Queue on the keyA transaction-scoped advisory lock on user and key: identical requests wait for each other
  4. 04Lock in orderBoth accounts are locked FOR UPDATE, always in the same order
  5. 05PostDebit and credit written; balances and sequence numbers updated
  6. 06Same transactionThe audit entry and the outbox event commit with the transfer, or not at all
  7. 07CommitThe deferred trigger checks that the transfer balances
  8. 08ReplayA retry with the same key gets the stored response; the same key with a different body is refused

decision 01

Lock accounts in one global order

Constraint
Two transfers between the same accounts in opposite directions each lock one account and then wait for the other: a deadlock.
Decision
One component decides the lock order for every code path that locks more than one account, and SQL never decides it with an ORDER BY.
Result
1,800 crossed transfers between two accounts in the load test, with no deadlock.
Trade-off
Writers to one busy account queue behind each other, and while they wait they hold database connections.

That trade-off is the main open issue the load test found: transactions queuing on a hot account's lock keep their connections, so a burst on one account slows unrelated ones. A larger pool made it worse. A limit on concurrent writes is the chosen direction; it is designed, not implemented.

04 / Sessions & security

Money moves only on a session the server still trusts.

Access tokens are short-lived and held only in memory; the refresh token lives in an HttpOnly cookie and rotates on every use. Presenting a refresh token that has already been used is treated as a stolen token: the whole session family is revoked, and the revocation is audited in the same transaction.

Passwords
Argon2id with OWASP-recommended parameters. Five failed sign-ins lock the account, counted in one atomic update.
Current authorization
A token issued before a password, role or status change can still read for up to ten minutes, but it can no longer move money.
Endpoint matrix
Every registered endpoint must be classified in a test. An unclassified one fails the build, and every write requires current authorization.
Audit
Written in the same transaction as the action it records, in a table that is append-only by privilege.
Masked absence
Someone else's account and a missing one get the same 404, the same work and the same audit entry.
Payee check
The payee is confirmed by first name and initial only, before anything is sent.

Two details came from testing the interface in a real browser. A double click on the confirmation sends exactly one request, because the guard runs before React re-renders. And when no attempt gets an answer, the page asks the bank for the outcome of that key and shows the saved receipt: it never reports a failure it cannot know, and it never sends twice.

05 / Testing & load

Tests that force the race, and load tests that audit the books.

The backend suite runs 144 unit tests and 211 integration tests with ./mvnw verify, the integration tests against a real PostgreSQL container. Concurrency tests do not hope for a race: they hold a lock, wait until the database shows the other transaction blocked, and only then release, so each interleaving is forced. The frontend has 38 Vitest tests and end-to-end scenarios in Playwright with Chromium.

Load tests use k6 in an open model, against a separate database that refuses to run unless it is marked for performance testing. After every scenario, twelve accounting checks run in one snapshot, the k6 counts are compared with the database, and the application's reconciliation has to pass. A Prometheus and Grafana profile reads the backend's metrics from a separate management port, with dashboards generated from code rather than edited by hand, and when the connection pool runs dry the API answers 503 with Retry-After instead of failing with a 500.

06 / Boundaries

Simulation limits, and what is still open.

Money
None. A simulated bank built for learning: no real accounts, no payment network, no regulated service.
Deployment
Runs locally with Docker Compose. There is no hosted instance.
Performance
Figures from one laptop and one run each: they are not production capacity.
Open issues
A hot account can exhaust the connection pool, and the analytics backfill rereads the whole ledger at start-up: about 71 minutes at 5 million entries.

what it demonstrates

Transactional design in Java and Spring Boot: a ledger the database itself keeps balanced, idempotency and lock ordering that hold under concurrency, rotating sessions with reuse detection, and measurement used to find the next problem to solve.

what it is tested with

JUnit unit and integration tests against a real PostgreSQL container, an architecture test for module boundaries, Vitest and Playwright on the frontend, and k6 load scenarios followed by accounting checks.
