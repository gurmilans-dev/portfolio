# Gurmilan Singh portfolio

A framework-free static portfolio for a full-stack software engineer, with no runtime npm dependencies and no tracking.

The design treats every project as a cut through four layers — **L4 Interface, L3 Application, L2 Data, L1 Delivery**. On the homepage the six featured systems sit in an interactive CSS-3D stack: selecting a system draws a beam through its socket on every plane and shows its layer-by-layer file beside the stack. Each system then offers two ways in, named for what they are: a **Quick look** (a drawer, previewed by the project's own screenshot, that adds what the panel beside it does not show: the screenshot, the key decision and the evidence) and the **Full case study** (its own page). On phones and tablets the selected system's summary, screenshot preview and case study link come straight after the system tiles, and the stack follows them; the stack never stands between a choice and what was chosen. Work that does not have those four layers, or is smaller, earlier or still moving, is listed below the explorer in the **Also built** register and described with an architecture chain and a flow instead of invented layers. Every row ends in the same actions in the same order: Quick look, the full case study where there is one, then the Chrome Web Store listing and the GitHub repository, each named in words.

Each project shows two separate facts: its **status**, which is how far it has come (production, deployed, published, pilot preparation, in development, runs locally, experimental, commercial, academic), and its **source**, derived from `repository` ("Public source", "Private source" or "Confidential").

Every case study opens with its evidence: right under the title, a real screenshot (for the confidential platform, the before-and-after) beside the one or two verified results that matter most, each linked to the section that explains it. The four-layer cut sits in the architecture section, as a summary of what that section explains.

## Run locally on Windows

1. Open PowerShell in this folder.
2. Install development dependencies: `npm ci --include=dev`
3. Build: `npm run build`
4. Run the HTML regression tests and site validation: `npm test`
5. Run the browser tests: `npm run test:browser` (needs Chrome, Chromium or Edge; set `CHROME_PATH` if it is not in its usual place)
6. Serve the production folder: `npm run serve`, then open `http://localhost:4173`

`scripts/serve.mjs` serves `dist/` the way the host does: pages at clean URLs (`/flowbank-one`), `/page.html` answered with a 307 to the clean URL, `_redirects` applied, and `404.html` with a 404 status for anything else. Opening the built files directly from disk is not supported, because links are root-relative.

The root HTML files are source templates. Essential values and repeated markup are resolved into complete static HTML during the build; content and navigation never depend on JavaScript.

## How the pages are built

- `site.config.mjs` — profile, contact form, the four layers, and every project: copy, status, evidence, what is *not* claimed, layer summaries, architecture, decision record and images. This is the single source of truth for the workbench order and the case files.
- `scripts/components.mjs` — build-time partials (`{{> head-boot}}`, `{{> header home}}`, `{{> footer}}`, `{{> wb-index}}`, `{{> wb-stage}}`, `{{> wb-files}}`, `{{> wb-mode}}`, `{{> wb-universe}}`, `{{> also-built}}`, `{{> drawer}}`, `{{> case-cut key}}`, `{{> case-end key}}`, `{{> case-index key}}`, `{{> case-status key}}`, `{{> case-source key}}`, `{{> github-link key}}`, `{{> sim id}}`, `{{> inspect key}}`) rendered from the config. `github-link` renders nothing unless the project has a public GitHub repository; `case-source` shows that link once it exists and the words "Private repository" until then.
- `scripts/sims.mjs` — the two simulations' scenarios and steps, and the markup made from them (see below).
- `scripts/universe-data.mjs` — Project Universe's data, made at build time from the projects and the `universe` block in `site.config.mjs`, and written into `assets/universe.js` (see below). It fails the build on an unknown project, domain or concept, a project with no place or no relationship, or a relationship without an explanation.
- `scripts/search-index.mjs` — the command palette's index, made at build time from the projects in `site.config.mjs` and the sections of the built case studies (see below).
- `build.mjs` — partial and token resolution, conservative CSS/JS minification, comment removal, sitemap, robots and search-index generation, static and media copy. The sitemap and `robots.txt` exist only in `dist/`, generated from `siteConfig.pages` with the clean URLs the pages declare as canonical; the host publishes `dist/` alone, and `validate.mjs` refuses a stale `sitemap.xml` in the source folder. It also turns every internal link and asset path into a root-relative, clean URL (`erp-case-study.html` becomes `/erp-case-study`, `index.html#work` becomes `/#work`): templates and `site.config.mjs` keep writing file names.
- `validate.mjs` — run by `npm test`: metadata, canonical URLs and the sitemap, links and fragments, unique ids, accessibility contracts, workbench order against the config, and the claim checks that keep every case study honest (no invented usage, deployment or technology).
- `scripts/browser.test.mjs` — run by `npm run test:browser` against the built site, in headless Chrome driven by `scripts/cdp.mjs` (no dependencies; Node 22+). It checks behaviour the validator cannot see: the small-screen menu with and without its script, focus after a quick look closes, `#work-` links (valid, unknown and malformed), the selected system's summary on narrow screens, the stage controls on short windows, Reset view, themes, internal links, the contact form against intercepted requests (nothing is sent), the 404 page at a nested path, layout shift while pages load, input during transitions, every path through the two simulations (keyboard, touch, every width and step, both themes, contrast, reduced motion, without JavaScript, a slow or blocked `sims.js`), Inspect mode (every part's annotation, keyboard, touch, zoom, layout at every size, reduced motion, without JavaScript, a slow `inspect.js`) and the command palette (shortcuts, the Search control, searches and their destinations, actions, a phone sheet, ARIA wiring, lazy loading and a missing index), and the hero-to-explorer transformation (both directions and exact hand-overs at several window sizes, fast scrolls and jumps, `#work`, input during and after it, a deep link and Back, reduced motion, without JavaScript, `DOMMatrix`, `requestIdleCallback` or `ResizeObserver`, both themes, the in-place fold on narrower and short windows by touch, layout shift, a focused hero plate, a slow device, and a browser that draws the stage's floors on one plane), and Project Universe (Architecture as the default and restored exactly, all thirteen projects named without overlaps, selection by node, label, list, select and related project, every project's destinations, domains, connections and shared technologies, orbit, tilt, zoom by slider, Ctrl and the wheel or two fingers, a plain wheel that scrolls, Reset and Focus, a still map that draws nothing, keyboard, touch, reduced motion, signals that stop off screen and when closed, the hero's drawing left as it is, seven window sizes, no JavaScript, and both themes).

## Publishing a private repository

FlowBank One, ProcBeacon, Orbit, Opssemble and Alfaaz have private repositories, so their `repository` field in `site.config.mjs` is empty and no GitHub action is rendered for them. When one becomes public:

1. Paste its `https://github.com/...` URL into that project's `repository` field.
2. Run `npm run build` and `npm test`.

The GitHub action then appears in its homepage file and quick look, in its case study's facts and on its "Also built" row, and every "Private repository" source line switches to "Public on GitHub". No markup changes are needed. `validate.mjs` refuses any GitHub link on the site that is not a configured `repository`, so a private URL cannot be published by accident — which is also why private URLs must never be written into the config.

## Client scripts

- `assets/script.js` (every page): colour theme switch, navigation sheet, section awareness, reveal-on-scroll, case-study sequences, screenshot hotspots and lightbox, contact form, copy-to-clipboard, the Modena clock. The small-screen menu is drawn as a sheet from the first paint (`.nav-pending`, set in `<head>`), but it only becomes the working menu once this script has wired it (`.nav-ready`); if the script is blocked or fails, the pending state is dropped at DOMContentLoaded and the plain links come back.
- `assets/workbench.js` (homepage): hero tilt, the systems tablist, the stack (orbit, explode, layer highlighting), the quick-look drawer, the hero-to-explorer transformation, and the switch between the explorer's Architecture and Universe views.
- `assets/universe.js` (never loaded up front, about 12 KB compressed with its data): Project Universe. `workbench.js` loads it the first time Universe is chosen (a moment earlier when that button is hovered, focused or touched).
- `assets/sims.js` (FlowBank One and ProcBeacon case studies only, about 5 KB): steps the simulations. It never talks to the network, a database or a process.
- `assets/inspect.js` (MaintOps, Opssemble and Gurmat Saanj case studies only): Inspect mode for one screenshot on each.
- `assets/palette.js` (never loaded up front): the command palette. `script.js` loads it on Ctrl+K / Cmd+K or the Search button (a moment earlier when that button is hovered or focused), and it fetches `assets/search-index.json` the first time it opens.

The inline head script follows the stylesheet link directly, on every page. Being a script, it makes the parser wait for `styles.css` before reading the body, so a page's view-transition opt-in is in force before anything can ask for it: Chromium otherwise sometimes evaluated an arriving page without it and abandoned the transition (reproduced in Chrome under Playwright in about half of the explorer-to-case-study trips, none after the move). Rendering waits for the stylesheet anyway, so the theme is still applied before the first paint. `validate.mjs` keeps the order.

## Break it yourself: the two simulations

The FlowBank One case study (Ledger & concurrency) and the ProcBeacon case study (Process safety) each carry a small instrument labelled as a simulation, beside the decision record it puts to the test:

- **FlowBank One, lock order:** two crossed transfers, in FlowBank's order, out of order (the deadlock the rule prevents, PostgreSQL's `40P01` and FlowBank's single retry), and a lock held past `lock_timeout` (`55P03`, `503 ACCOUNT_BUSY`). Taken from `AccountLockOrder`, `PostingService`, ADR-0005, `LedgerConcurrencyIT` and the performance report.
- **ProcBeacon, PID reuse:** a PID that passes to another program between the refresh and the click (blocked as `IdentityChanged` on the handle), the same process ended and verified on its handle (the session then refuses a second run), and a critical process with an ordinary name. Taken from `WindowsProcessControlService`, `ProcessControlPolicy`, the confirmation window and `ProcessControlTests`. The processes, PIDs, times and paths are invented.

`scripts/sims.mjs` holds the steps, and the build renders three things from them: a written transcript (what a reader without JavaScript gets, and what prints), the live instrument already drawn in its start state, and the steps as JSON for `assets/sims.js`. The live view is shown from the first paint under `.sim-pending` (dropped at DOMContentLoaded unless `sims.js` took over), so nothing moves when the script arrives, and nothing changes size while it steps: lines of different length are stacked in one cell. Step, Back, Reset, Play and the step rail are buttons; arrow keys, Home and End step while focus is on the controls; each step is announced through a polite live region.

## From the drawing to the model

The hero's figure (Fig. 00: the four layers drawn as an elevation of cards, each naming what it is built with) and the explorer's stack (Fig. 01: the same four layers seen from above, cut through by each system) are one object, and on wide screens one turns into the other as the page scrolls. From 960px wide and 560px tall, a copy of the four plates lies exactly over the drawing from the first pixels of scroll. With the scroll each card tips back, turns and squares into a floor, its technologies drain into the selected system's socket, and the floors come to rest exactly where the stage's own stack is (to within a fraction of a pixel). The copy travels to wherever the stage is: the middle column from 1280px, under the systems from 960px. The systems and the selected system's file stay above the floors as they pass. There the stage's stack takes over and draws the cut through the floors.

It follows the scroll position and nothing else: scrolling back plays it back, a fast scroll or a jump lands where it lands, nothing is held or delayed, and `#work` and every deep link open on the explorer as before. The copy is an `aria-hidden`, inert layer that `workbench.js` builds while the page is idle. The real figures stay in the page throughout, only transparent while the copy travels, so reading order, links and focus never change; a keyboard visitor on a hero plate sees the drawing itself. Sizes, content and colours are set up once, so a frame of scroll changes only transforms and opacity, on a few elements, and lays nothing out.

Narrower windows, and short ones, get the same gesture in place: the drawing tips back and parts into floors as it leaves the screen, and the stage's floors close up as they arrive. Reduced motion, no JavaScript and browsers without `DOMMatrix` keep both figures as they are. So does a browser that does not actually draw the stage's floors apart in depth: some engines accept `transform-style: preserve-3d` (`CSS.supports` and the computed style both say so) but lay all four floors on one plane, as Playwright's WebKit build does, and the copy's four floors would then have nothing to land on. Before it runs, `workbench.js` checks where the stage's floors really are; if they are drawn in one place, the transformation stands aside. So does a device that cannot build the copy quickly: the build is timed, and if it takes more than about three frames, a second build is timed a moment later; if that one is slow too, the transformation steps aside before any scroll needs it.

## Project Universe

The explorer has two views, chosen by a switch under the section's heading. **Architecture** is the explorer above, unchanged, and is what every page load starts on. **Universe** is a 3D map of all thirteen projects (the six systems and the seven in Also built) and what they share. Each view keeps its state while the other is shown: coming back to Architecture finds its system, layer, spacing and angle as they were, and Universe first opens on the system that was selected in Architecture.

- **What it shows.** Each project is a small cube at its own place in one space, in its domain's colour (Business & operations, Developer tools, Personal & community, Learning & experiments), standing over a projected ground grid with circular guides. The selected project has a dashed ring and a soft glow, and its relationships are drawn in orange with a signal travelling outward along each. A relationship is a shared technology or engineering concern, never a dependency, and each one says, in a sentence, what the two projects share and how each does it. They live in the `universe` block of `site.config.mjs`, with the evidence for each in a comment; names, categories, summaries, technologies, statuses and destinations come from the projects themselves.
- **Using it.** A project is selected on its node, its label, the list beside the map (from 1280px; a select stands in for it on narrower screens) or a related project in the panel. The panel gives its domain, category, status, source, summary, technologies and concerns, its relationships in words, and its destinations: a quick look, the full case study, the Chrome Web Store and GitHub, only where they exist. A technology or concern another project shares highlights every project that lists it. The domains filter the map, keeping the others faintly in place; All connections draws every relationship. A drag orbits and tilts the camera (on touch, a sideways swipe orbits and a vertical one scrolls the page), two fingers or Ctrl with the wheel zoom, and a plain wheel always scrolls the page. Buttons orbit, tilt, zoom, reset the view and turn the selected project to the front (Focus); selecting a project never moves the camera.
- **Drawing.** An SVG drawn with a perspective projection of real 3D coordinates (the reference prototype's camera and composition), so nodes, connections, grid, guides and labels turn as one. Its elements are made once and only their attributes change; labels are placed where they overlap no other label and cover no other node, keeping their last place while the map turns. The camera eases in time and the loop stops when it arrives, so a still map runs no script; the signals are small dots under the drawing, moved by their transform alone (Web Animations, run by the compositor, so the drawing is never repainted for them), paused while the map is closed, off screen or in a hidden page, and absent with reduced motion, which also moves the camera at once.
- **With the rest of the page.** While Universe is shown the hero's drawing stays as it is (there is no model for it to turn into); back in Architecture it turns into the model again. A link to one of the six systems (`#work-<system>`) shows Architecture. Without JavaScript neither the switch nor the map exists, and the plain list of every system remains.

## Transitions and the contact response

Moving between pages uses the browser's own cross-document view transitions (`@view-transition` in `assets/styles.css`), opted into only when the visitor has no reduced-motion preference. A project's name and its primary screenshot carry one transition name per project (`vt-title-<key>`, `vt-shot-<key>`), so they travel from the explorer's panel to the case study's eyebrow and evidence band, from a case study's pager card to the next case study, and back; the header stays in place and the rest of the page crossfades. Previous/Next in the case-study pager and history Back/Forward add a short sideways drift. The inline head script (`headBoot` in `scripts/components.mjs`) handles arrival: it marks the page so load animations do not replay underneath, adds the direction, and only lets elements that are on screen travel. Opening and closing a quick look is a same-document view transition where `document.startViewTransition` exists: the panel's preview grows into the drawer's screenshot as the drawer slides in. Browsers without view transitions, and reduced motion, get ordinary navigation and the drawer's own slide; nothing waits on a transition.

The contact form's footer shows its states as a small lane in the marks of the hero's request trace: Check, Send, Received. It mirrors the status line (which stays the only live region and the source of truth), moves only while a request is out, and reaches Received only after the form service answers with success. Without JavaScript it stays hidden and the form posts normally.

## Inspect mode

Three case studies let a visitor take one real screenshot apart: the MaintOps supervisor dashboard, the Opssemble readiness view and the Gurmat Saanj operator workspace. Each has four parts, defined in the project's `inspect` entry in `site.config.mjs` (a box in the image's own pixels, and what the part does, what is behind it, why it matters, a decision where there is one, and English for the Italian on screen). Every statement comes from the project's source and documents; the config names the files.

The build renders the notes as a closed list under the screenshot ("What the … shows"), which is all there is without JavaScript, and an Inspect button that `inspect.js` reveals. The inspector lays the screenshot on a drafting grid beside a reading panel: the parts are tabs over the image (arrow keys move between them, Tab reaches the explanation), the chosen part is lit and the rest dimmed, and Zoom to part scales the screenshot until the part fills the stage. On a phone it opens zoomed, with the part navigation pinned under the notes. With a fine pointer the parts outline themselves on the page's screenshot, and a click there opens the inspector on that part; keyboard activation of the screenshot still opens the full-size image, as its label says.

## Command palette

Ctrl+K (Cmd+K on a Mac), or the Search control in the header, opens a palette over any page. It searches an index built from what the site publishes: every project in the explorer (name, category, summary, technologies), every section of every case study (its number, title, inner headings and text, read from the built page) and the homepage's places. A result can only lead to a page or section that exists, under its own name; `validate.mjs` checks every destination. Search runs on the device: whole words outrank word starts, a short word ("Java") means itself once something matches it whole, and one small, documented table lets "authentication" find the pages that speak of sign-ins, tokens, credentials and passwords. The actions are the site's own: switch the theme, download the CV, copy the email address. Escape closes it and returns focus; a phone gets a full-height sheet.

## Themes

Dark (graphite) and light (drafting film). A first visit follows the system setting; the Dark / Light switch in the header stores an explicit choice in `localStorage` under `portfolio-theme`, and a small inline script in every page's `<head>` applies it before the first paint. All colours are custom properties in `assets/styles.css`: the dark values sit on `:root`, the light values on `:root[data-theme="light"]`, repeated inside a `prefers-color-scheme: light` query so pages without JavaScript still follow the system. `validate.mjs` fails the build if the two light blocks differ or a colour token has no light value. In light mode the bright signal orange stays on filled surfaces (`--accent-fill`, with dark ink) while text and lines use a deeper orange (`--accent`) that clears 4.5:1.

The homepage's contact section and footer reverse figure and ground in both themes: a slightly deeper shade of the signal orange (`#ea7a2e`) becomes the ground, and the left column and footer line swap their text, line and accent tokens for graphite-ink tones that clear 4.5:1 on it (3:1 for control edges). The form keeps the reader's theme as a plate on the orange, on the same offset slab as the hero plates.

## Fallbacks

Without JavaScript the workbench is a plain list of every system with its full case file (and the explorer's Universe view and its switch do not exist), each simulation is its written transcript, each inspectable screenshot keeps its notes as an openable list, and the Search control is simply absent. Reduced-motion preferences disable the load sequence, the ambient drift, and the request/response trace and release pipeline in the hero figure, which then rests in its final state; the hero's drawing and the explorer's stack then stay as they are instead of turning into one another. The 3D stack is decorative and hidden from assistive technology; the same information is in the index and the layer files.

## Production deployment

Deploy the contents of `dist/` to any static host. Configure the host to use `404.html` for unknown routes. The site is built for the host's default HTML handling on Cloudflare (`wrangler.jsonc`): pages live at clean URLs and `/page.html` redirects to them, so canonicals, Open Graph URLs, the sitemap and every internal link use the clean URL. Old addresses go in `_redirects`, pointing straight at the clean URL so they take one hop.
