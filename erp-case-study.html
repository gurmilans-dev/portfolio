01 / Overview

One application, one relational source

The platform brings business records, time, scheduling, administration and reporting into one application, instead of the same information being kept again in separate files.

Replacing the old tools meant supporting concurrent use across teams without losing control of the data or of who may change it. Because the screens, the API and the data are one system, a change to a form, a rule or the data model is planned and released as one change.

03 / Responsibility

Primary development across the full stack

Requirements come directly from internal users. My work covers interface and API features, relational design, permissions, releases, maintenance and support.

I clarify the user’s goal, trace the records and roles involved, implement the smallest coherent change across the stack, and review the result with the people who asked for it. That loop matters most when a screen change touches existing data or access rules.

04 / Architecture and access

Role checks stay beside application logic

{{> case-cut erp}}

decision 01

Authorize modules and actions by authenticated role

Different responsibilities need different access, so I keep authorization on the server: a user's role decides which modules and actions they can reach, and the interface only mirrors what the API already enforces. The cost is that every new feature has to carry its own permission rule.

05 / Quality and maintenance

A change is not finished at deployment

Input validation, relevant automated regression checks, manual verification and direct user feedback protect important behaviour. Test counts and coverage are not published.

For a defect, I first reproduce the conditions the user reported, then check whether the cause sits in interface state, API logic, permission handling or stored data before changing code. After the release I confirm the fix with the person who reported it.

06 / Outcome

Shared software with continuing ownership

result

The platform replaced disconnected legacy tools and brought previously separate records into one application, in daily use since.

lesson

Production work requires careful data changes, clear permissions, release discipline, and support after delivery.
