04 / AlfaazPrivate multilingual writing system

Somewhere to write that keeps nothing it does not need.

Alfaaz is a writing environment for poetry, fragments and longer-form work across English, Hindi and Punjabi. Interface language and writing language are independent, and what you write is never automatically translated. It is a private repository and is not publicly deployed.

01 / Product

Three languages, and no opinion about which one you think in.

Most writing tools treat a second script as a localisation problem: pick a language, and the whole product follows. That is the wrong shape for someone who reads an interface in English, writes shayari in Gurmukhi, and drafts a note in Devanagari on the same evening.

So the two are separated. The interface language is a preference with three full locales; the language of an entry is simply whatever was typed into it. Nothing in the system reads an entry to decide what language it is in, and nothing translates it. That restraint is the product.

the whole navigation

  • TodayThe current day, and quick capture for fragments
  • WriteOne editor, with focus mode when the room needs to disappear
  • Library & CalendarSearch, filters, and everything by date
  • Collections & BooksGrouping, and manuscripts assembled from existing entries

Five destinations, deliberately. Every feature that arrived later — voice notes, ambience, postcards, exports — attached itself to one of them rather than earning a sixth tab.

02 / Architecture

A boring server, so the editor can be interesting.

03MySQL18 tables · 15 migrations

The server is layered routes → controllers → services → repositories, and every write that touches more than one row runs inside a transaction with an explicit rollback. Repositories hold parameterized SQL directly; sort orders map to a fixed set of hard-coded fragments rather than being interpolated from the query string.

There is no ORM. That is worth stating only because it explains the shape of the code above: when the repository is the only thing that writes SQL, a rule like every user-owned read is scoped by user_id is enforceable by reading one folder. The schema grew through 15 numbered migrations, so each feature — saved atmospheres, voice notes, books, typography, data transfer, account security — arrived as a reviewable change to the data model rather than an edit to a single evolving file.

03 / Writing system

The editor autosaves constantly and still refuses to lose your work.

Autosave and version safety pull in opposite directions. Saving often means writing constantly; not losing anything means never letting a stale tab overwrite a newer save. Alfaaz resolves it with a version number on every entry and a server that would rather fail a write than accept a doubtful one.

technical artefact · the write path

  1. 01KeystrokeRoman, Devanagari or Gurmukhi — the editor does not care which
  2. 02Transliteration assistRuns in the browser; Space accepts, Escape keeps the Roman text
  3. 03Debounced autosaveUnsaved text is held on the device until the save lands
  4. 04Ownership checkThe row is fetched by id and user, and locked for update
  5. 05Version checkA mismatch raises a conflict and the write is refused — never merged silently
  6. 06CommitEntry updated, version advanced, transaction closed
  7. 07Restore, laterRestoring a revision first archives the current text as a new revision

Step 07 is the one that took the longest to get right. A naive restore is destructive: you recover last week's stanza and lose this morning's. Here the restore runs in a single transaction that locks the row, checks the version, writes the current text into the revision history, and only then applies the older text — so the operation you performed to recover something can itself be undone.

Books work on the same instinct. A manuscript holds references to entries rather than copies of them, so editing a poem updates the book, and a soft-deleted source visibly blocks export instead of quietly exporting a stale duplicate.

04 / Privacy decisions

Privacy as a property of the queries, not a paragraph in the settings.

A private journal makes a specific promise, and the only version of that promise worth making is one the architecture keeps even if the interface has a bug.

decision 01

Store a digest of the session token, never the token

Constraint
Sessions must survive restarts and be revocable, which means persisting something.
Decision
Issue an opaque 256-bit random token in an HttpOnly cookie and persist only its HMAC-SHA-256 digest.
Result
Read access to the sessions table does not yield a usable credential. Client IP addresses are stored the same way — hashed with a secret, never in the clear.
Trade-off
The digest secret becomes part of the deployment's security surface: rotating it invalidates every live session.
Ownership
User-owned rows are fetched by identifier and user together. A row that is not yours is not "forbidden" — it does not exist, and the API answers 404.
Voice notes
MySQL stores metadata only. The audio bytes live outside anything served statically and stream through an authenticated per-entry route.
Focus sessions
Writing-session timing stays in browser storage with no database table at all — the server is never told how long someone sat with a blank page.
Local music
Device audio is played through temporary object URLs and never uploaded.
Exports
Postcards and PDFs are rendered client-side. No file and no export history is stored, and author and date are off by default.
Data transfer
Export and import jobs record counts and outcomes — never the contents that moved.

Only the built client is served as static files. Everything user-owned goes through a route that knows who is asking.

05 / Design & language

Three scripts that all have to look intentional.

Latin, Devanagari and Gurmukhi have different vertical metrics and different ideas about where a line sits. Setting them in one stylesheet means pairing Lora with Noto Serif and Sans in each script and then accepting that a single line-height will not serve all three equally.

constraints that are enforced, not documented

  • PaletteEight approved colours, checked by a build-time validator over the brand assets
  • TypographyPer-entry and per-book typography, so a poem can be set differently from a journal
  • Export renderingPDF pages are drawn to canvas so Indic text shapes correctly instead of decomposing
  • AmbienceSix mixable channels that never autoplay after a reload

The export constraint is the interesting one. Generating a PDF by writing text runs into font-shaping limits for conjuncts and matras; rendering the page to a canvas first and placing that in the document costs file size and selectable text, and buys correctly shaped Gurmukhi. For a manuscript of someone's poetry that is the right side of the trade.

06 / Boundaries

What this project does not claim.

Repository
Private. There is no public source to inspect, which is a real limitation of this case study.
Deployment
Not publicly deployed. There is no hosted instance and no public URL — it runs locally against MySQL.
Users
Built as a single-writer product. No user numbers are claimed because there are none to claim.
Transliteration
An assist, not a converter. It suggests; the writer accepts or keeps the Roman text, and ambiguous mappings stay ambiguous.
Voice notes
Recording depends on browser MediaRecorder support, and the available container format varies by browser.

what it demonstrates

Optimistic concurrency with a non-destructive restore path, ownership enforced in the data layer rather than the interface, a schema evolved through reviewable migrations, and multilingual typography carried all the way into generated documents.

what it is tested with

Component and unit tests with Vitest and Testing Library, server tests with Vitest and Supertest including opt-in integration runs against a separate test database, and an end-to-end Playwright suite covering auth, mobile, exports, transliteration and voice notes.
